# 🧪 Лабораторный практикум: Модуль 04 — Управление процессами и Systemd

## 📋 Общие инструкции

Практические работы этого модуля моделируют реальные эксплуатационные задачи инженера по сопровождению Linux-систем: управление приоритетами CPU, локализацию зависших процессов, разработку защищенных юнитов Systemd, миграцию с устаревшего Cron на Systemd Timers и расследование сбоев высокой степени критичности.

Все исходные материалы находятся в каталоге `starter_data/`:
* `mock_daemon.py` — приложение-микросервис с поддержкой сигналов POSIX и симуляцией аварийных состояний.
* `broken_service.service` — шаблон сломанного юнита Systemd с 5 архитектурными ошибками.
* `load_generator.sh` — утилита генерации нагрузки и отправки тестовых сигналов.
* `backup_task.sh` — регламентный скрипт бэкапа для отработки таймеров.

## 🛠️ Лабораторная работа 1: Анатомия процессов, управление сигналами и приоритетами (Nice / Signals)

### 🏢 Бизнес-контекст
На многопользовательском сервере разработки несколько ресурсоемких математических задач полностью загрузили ядра CPU, вызвав деградацию скорости отклика критических системных демонов. Администратору необходимо:
1. Выявить процессы-пожиратели ресурсов.
2. Скорректировать их приоритеты планирования без перезапуска.
3. Отработать правильный двухфазный сценарий остановки процессов (Graceful Shutdown через `SIGTERM`, затем принудительное уничтожение через `SIGKILL`).

### 🎯 Технические требования:
1. В каталоге `starter_data` запустите генератор нагрузки:
   ```bash
   ./load_generator.sh --cpu 2
   ```
2. Откройте `top` или `htop` и зафиксируйте текущие значения CPU (`%us`, `%sy`, `%id`), а также значения `Load Average`.
3. С помощью команды `ps` выведите список запущенных процессов нагрузки с отображением колонок: `PID`, `PPID`, `NI` (Nice), `PRI` (Priority), `%CPU`, `STAT`, `COMMAND`.
4. Для первого процесса понизьте приоритет до самого "вежливого" значения (`NI = +15`) с помощью команды `renice`.
5. Для второго процесса установите приоритет с повышенным выделением квантов CPU (`NI = -10`). Обратите внимание, почему для этого требуются привилегии `sudo`.
6. Исследуйте структуру директории одного из процессов в виртуальной файловой системе ядра `/proc/<PID>`:
   * Просмотрите аргументы запуска через `/proc/<PID>/cmdline`.
   * Изучите текущие лимиты открытых файлов и процессов в `/proc/<PID>/limits`.
   * Проверьте открытые дескрипторы в `/proc/<PID>/fd/`.
7. Выполните остановку процессов:
   * Отправьте сигнал `SIGTERM` (15).
   * Если процессы не завершились в течение 5 секунд, примените принудительный сигнал `SIGKILL` (9).
8. Убедитесь с помощью `./load_generator.sh --status`, что фоновые нагрузочные процессы завершены.

## 🛠️ Лабораторная работа 2: Создание и харденинг production-grade службы Systemd

### 🏢 Бизнес-контекст
Команда разработчиков передала в эксплуатацию микросервис `mock_daemon.py` вместе с конфигурационным файлом `broken_service.service`. При попытке запустить службу система выдает ошибки. Кроме того, юнит нарушает корпоративные стандарты безопасности (пытается работать от root, не имеет защиты от неконтролируемого рестарта и может исчерпать всю оперативную память хоста).

### 🎯 Технические требования:
1. Подготовить директорию приложения:
   * Скопировать `mock_daemon.py` в `/opt/mock_daemon/mock_daemon.py`.
   * Назначить права на исполнение (`chmod 755`).
   * Убедиться, что владельцем файла является пользователь `student`.
2. Исследовать `starter_data/broken_service.service` и устранить **5 критических дефектов**:
   * Ошибка пути: заменить относительный вызов на абсолютный путь `/usr/bin/python3 /opt/mock_daemon/mock_daemon.py`. Убрать флаг `--crash-on-start`.
   * Неверный тип: заменить `Type=forking` на правильный `Type=simple`.
   * Безопасность: добавить запуск от пользователя `User=student` и группы `Group=student`.
   * Защита от спама рестартов: настроить `Restart=on-failure`, интервал ожидания `RestartSec=3s`, лимиты `StartLimitIntervalSec=60s` и `StartLimitBurst=3`.
   * Автозагрузка: исправить опечатку `WantedBy=multi-users.target` на валидный таргет `WantedBy=multi-user.target`.
3. Добавить в секцию `[Service]` директивы харденинга и изоляции:
   * `ProtectSystem=strict` (запрет записи в системные директории).
   * `ProtectHome=true` (запрет доступа к каталогам `/home`).
   * `NoNewPrivileges=true` (запрет повышения прав через SUID).
   * `PrivateTmp=true` (изолированный `/tmp`).
4. Настроить ограничения ресурсов через **cgroups v2**:
   * `CPUQuota=50%` (не более половины одного ядра CPU).
   * `MemoryMax=256M` (жесткий потолок оперативной памяти).
5. Добавить директиву перечитывания конфигурации:
   * `ExecReload=/bin/kill -HUP $MAINPID`.
6. Сохранить готовый файл в `/etc/systemd/system/mock_daemon.service`.
7. Зарегистрировать изменения (`systemctl daemon-reload`), включить сервис в автозагрузку и запустить:
   ```bash
   sudo systemctl enable --now mock_daemon.service
   ```
8. Проверить статус службы (`systemctl status mock_daemon.service`) и выполнить тестовый HTTP-запрос:
   ```bash
   curl -s http://localhost:8088/status
   ```

## 🛠️ Лабораторная работа 3: Systemd Timers — замена устаревшего Crontab

### 🏢 Бизнес-контекст
Ранее регламентное резервное копирование запускалось через `crontab`. Во время плановых ночных перезагрузок серверов бэкапы пропускались, а администраторы не получали никаких уведомлений. Требуется перевести задачу создания бэкапов на **Systemd Timers** с гарантией выполнения пропущенных задач (`Persistent=true`) и централизованным логированием в `journald`.

### 🎯 Технические требования:
1. Скопировать регламентный скрипт `starter_data/backup_task.sh` в системную директорию `/usr/local/bin/backup_task.sh` и выдать права на исполнение (`chmod 755`).
2. Создать юнит службы однократного запуска `/etc/systemd/system/app_backup.service`:
   * `Type=oneshot`.
   * `ExecStart=/usr/local/bin/backup_task.sh`.
   * `User=root`.
3. Создать юнит таймера `/etc/systemd/system/app_backup.timer`:
   * Настроить запуск каждые **10 минут** (`OnCalendar=*:0/10`), либо через 2 минуты после старта таймера (`OnActiveSec=2min`).
   * Включить директиву `Persistent=true` для отработки пропущенных интервалов.
   * Связать таймер с `timers.target`.
4. Применить конфигурацию (`systemctl daemon-reload`) и запустить таймер (`systemctl enable --now app_backup.timer`).
5. Проверить статус всех таймеров системы с помощью команды:
   ```bash
   systemctl list-timers app_backup.timer
   ```
6. Выполнить ручной тестовый прогон службы:
   ```bash
   sudo systemctl start app_backup.service
   ```
7. Убедиться, что архив создан в `/var/tmp/lab_backups/`, и проверить логи выполнения в журнале:
   ```bash
   journalctl -u app_backup.service
   ```

## 🛠️ Лабораторная работа 4: Инцидент-менеджмент: Траблшутинг аварийного падения через `journalctl`

### 🏢 Бизнес-контекст
Дежурная смена мониторинга зафиксировала отказ микросервиса `mock_daemon.service`. Статус сервиса изменился на `failed (Result: start-limit-hit)`. Перезапуск через обычный `systemctl restart` блокируется менеджером systemd. Необходимо оперативно провести расследование инцидента (Root Cause Analysis), устранить причину сбоя и вернуть сервис в эксплуатацию.

### 🎯 Технические требования:
1. Инициировать аварийную ситуацию на работающем сервисе `mock_daemon.service`:
   ```bash
   # Вызов критической ошибки через триггерный флаг
   sudo bash ./load_generator.sh --crash
   ```
2. Убедиться через `systemctl status mock_daemon.service`, что сервис перешел в состояние `failed`.
3. С помощью утилиты `journalctl` провести глубокий аудит логов:
   * Отфильтровать только логи сервиса `mock_daemon.service` за последние 10 минут.
   * Отфильтровать сообщения по уровню критичности `err` и `crit` (`-p err`).
   * Найти запись с текстом необработанного исключения и выяснить причину падения (RuntimeError / Crash flag).
4. Проверить и снять ограничение `start-limit-hit` с помощью команды:
   ```bash
   sudo systemctl reset-failed mock_daemon.service
   ```
5. Запустить сервис заново и подтвердить его работоспособность.
6. Проверить работу механизма перечитывания конфигурации на лету без прерывания соединений:
   ```bash
   sudo systemctl reload mock_daemon.service
   ```
7. Проверить в `journalctl`, что процесс перехватил сигнал `SIGHUP` и увеличил номер ревизии конфигурации без изменения PID процесса!

## 🧹 Очистка тестового окружения
После выполнения заданий остановите сервисы и удалите временные юниты:
```bash
sudo systemctl stop mock_daemon.service app_backup.timer 2>/dev/null || true
sudo systemctl disable mock_daemon.service app_backup.timer 2>/dev/null || true
sudo rm -f /etc/systemd/system/mock_daemon.service /etc/systemd/system/app_backup.*
sudo systemctl daemon-reload
sudo ./load_generator.sh --stop
```
