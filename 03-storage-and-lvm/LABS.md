# 🧪 Лабораторный практикум: Модуль 03 — Дисковая подсистема, файловые системы и LVM

## 📋 Общие инструкции и подготовка окружения

Все практические задания выполняются в безопасном окружении с использованием псевдоустройств (`loop devices`) и разреженных файлов, что полностью исключает риск повреждения вашей рабочей операционной системы.

Перед началом выполнения заданий перейдите в каталог `starter_data` и инициализируйте виртуальные диски:

```bash
cd starter_data
sudo bash ./setup_disks.sh
source /var/tmp/linux_lab_storage/loop_devices.env
```

После выполнения скрипт создаст 3 виртуальных накопителя:
* `$LOOP_DISK1` (1 GiB) — для работы с таблицами разделов GPT, ext4/XFS и Swap.
* `$LOOP_DISK2` (1 GiB) — для создания пула LVM.
* `$LOOP_DISK3` (2 GiB) — для масштабирования Volume Group и снапшотов.

## 🛠️ Лабораторная работа 1: Разметка диска GPT, создание гибридных ФС (ext4, XFS) и Swap

### 🏢 Бизнес-контекст
Вы пришли на должность системного инженера в FinTech компанию. В эксплуатацию вводится новый сервер для обработки транзакций. Архитектура сервиса предъявляет жесткие требования к дисковой подсистеме:
1. Журналы опережающей записи (WAL logs) требуют надежной файловой системы с журналированием и минимальным временем фиксации метаданных.
2. Аналитическое хранилище оперирует большими файлами отчетов и требует высокой производительности параллельного I/O.
3. Серверу требуется выделенный раздел подкачки (Swap) на случай пиковых нагрузок во время закрытия финансового периода.

### 🎯 Технические требования:
1. Создать на устройстве `$LOOP_DISK1` таблицу разделов **GPT**.
2. Разбить диск на 3 раздела:
   * **Раздел 1** (`p1`): размер **400 MiB**, тип `Linux filesystem`. Отформатировать в `ext4` с меткой `WAL_LOGS`. Отключить резерв 5% блоков для суперпользователя (`tune2fs`).
   * **Раздел 2** (`p2`): размер **400 MiB**, тип `Linux filesystem`. Отформатировать в `XFS` с меткой `ANALYTICS`.
   * **Раздел 3** (`p3`): оставшееся свободное место (около 224 MiB), тип `Linux swap`.
3. Смонтировать раздел 1 в директорию `/mnt/wal_logs` с опциями: `noatime,nodev`.
4. Смонтировать раздел 2 в директорию `/mnt/analytics` с опциями: `nosuid`.
5. Инициализировать и активировать область подкачки на Разделе 3.
6. Получить `UUID` всех созданных разделов и составить валидные конфигурационные строки для `/etc/fstab` (используя опцию `nofail`).
7. Проверить корректность монтирования через команду `mount -a`.

## 🛠️ Лабораторная работа 2: Архитектура LVM, онлайн-масштабирование и Snapshot Recovery

### 🏢 Бизнес-контекст
Основная СУБД компании MockDB хранит данные в LVM томе. Мониторинг сообщает, что свободное дисковое пространство приближается к критическому порогу 90%. Кроме того, отдел разработки собирается запустить рискованную миграцию базы данных `database_dump.sql`, которая в случае ошибки разрушит структуру таблиц. Вам поручено:
1. Развернуть отказоустойчивое хранилище LVM.
2. Скопировать рабочие данные СУБД.
3. Выполнить онлайн-расширение тома без остановки сервиса.
4. Создать консистентный LVM-снимок перед миграцией и отработать сценарий аварийного отката.

### 🎯 Технические требования:
1. Инициализировать блочные устройства `$LOOP_DISK2` и `$LOOP_DISK3` как **Physical Volumes (PV)**.
2. Объединить оба диска в единую **Volume Group (VG)** с именем `vg_db`. Убедиться, что размер Physical Extent (PE) составляет 4 MiB.
3. Внутри группы `vg_db` создать **Logical Volume (LV)** с именем `lv_mockdb` размером **1.5 GiB**.
4. Создать на томе `lv_mockdb` файловую систему `ext4` с меткой тома `MOCK_DATABASE`.
5. Смонтировать том в `/mnt/mock_db`.
6. Перенести исходные файлы СУБД из `/var/tmp/mock_db_source/` в каталог `/mnt/mock_db/`.
7. **Горячее масштабирование (Hot Online Resize)**:
   * Выполнить расширение тома `lv_mockdb` на **+1 GiB** (до суммарных 2.5 GiB) вместе с файловой системой одной командой `lvextend`.
   * Убедиться с помощью `df -h`, что файловая система увеличилась без размонтирования!
8. **Создание Snapshot и симуляция сбоя**:
   * Создать LVM-снимок `lv_mockdb_snap` размером **400 MiB** для логического тома `lv_mockdb`.
   * Смоделировать аварию: повредить файл базы данных:
     ```bash
     echo "CORRUPTED DATA BY JUNIOR DEV" > /mnt/mock_db/database_dump.sql
     rm -f /mnt/mock_db/mockdb.conf
     ```
   * Выполнить откат (merge) логического тома к снимку.
   * Смонтировать том обратно и подтвердить, что исходные файлы базы данных восстановлены в исходном виде!

## 🛠️ Лабораторная работа 3: Аварийное восстановление (Disaster Recovery: fstab & Inode Exhaustion)

### 🏢 Бизнес-контекст
Инженер дежурной смены сообщил о двух критических инцидентах:
* **Инцидент 1**: После ночных работ по изменению точек монтирования сервер не перезагружается штатно и сваливается в Emergency Shell. В репозитории доступен файл `starter_data/fstab.broken`.
* **Инцидент 2**: Сервер приложений выдает ошибку `write /var/log/app/trace.log: no space left on device`. Однако дежурный системный администратор утверждает, что команда `df -h` показывает 60% свободного места на разделе.

### 🎯 Технические требования:
1. **Расследование и починка `/etc/fstab`**:
   * Скопировать файл `starter_data/fstab.broken` в `/tmp/fstab.audit`.
   * Провести аудит каждой строки файла и выявить **5 критических ошибок** (несуществующий UUID без `nofail`, опечатка в типе ФС, некорректное число полей, несуществующая точка монтирования, сетевая ФС без `_netdev`).
   * Исправить все ошибки, закомментировав или приведя параметры к production-стандартам.
   * Проверить валидность исправленного файла с помощью `mount -fa --fstab /tmp/fstab.audit` (dry-run).
2. **Симуляция и ликвидация исчерпания Inodes**:
   * Создать тестовую точку монтирования `/mnt/inode_test`.
   * Смоделировать генерацию сотен тысяч микро-файлов (PHP sessions / mail spool) скриптом-генератором до полного исчерпания инодов (`No space left on device`).
   * Выявить проблему с помощью утилиты `df -i`.
   * Найти виновную директорию с помощью однострочника на `find` и удалить паразитные файлы.
   * Подтвердить доступность инодов.
