# Лабораторная работа 02: Разграничение прав доступа, POSIX ACL и аудит Sudo

## 🎯 Цели работы
1. Спроектировать безопасную модель совместного доступа к каталогам с использованием групп и бита **SGID**.
2. Защитить общедоступный каталог от несанкционированного удаления чужих файлов с помощью **Sticky Bit**.
3. Настроить гибкие права доступа для аудиторов и смежных отделов с помощью **POSIX ACL**.
4. Провести аудит безопасности конфигурации `/etc/sudoers` и устранить векторы повышения привилегий до root (GTFOBins).

---

## 📁 Стартовые данные
В каталоге `02-users-groups-and-permissions/starter_data/` подготовлены:
- `setup_users_and_shares.sh` — скрипт генерации пользователей (`dev_alice`, `dev_bob`, `auditor_charlie`, `fin_diana`), групп и каталога `/tmp/corp_storage`.
- `vulnerable_sudoers.conf` — фрагмент конфигурации sudoers с критическими ошибками для аудита.


## 📝 Задания

### Задание 1: Настройка совместной рабочей папки разработчиков с SGID
Каталог: `/tmp/corp_storage/projects`
**Требования:**
1. Владельцем каталога должен быть `root`, а группой-владельцем — `developers`.
2. Члены группы `developers` должны иметь полный доступ (чтение, запись, выполнение: `rwx`).
3. Любые другие пользователи системы (Others) не должны иметь к этому каталогу никакого доступа вообще (`---`).
4. **Критическое требование**: Настройте каталог так, чтобы любой новый файл или подкаталог, созданный любым разработчиком (хоть `dev_alice`, хоть `dev_bob`), автоматически получал группу-владельца `developers`, а не первичную группу создателя.
5. Протестируйте: создайте файл от имени `dev_alice` и убедитесь через `ls -l`, что группа файла автоматически стала `developers`.

---

### Задание 2: Общедоступный каталог обмена файлами со Sticky Bit
Каталог: `/tmp/corp_storage/public_drop`
**Требования:**
1. Все пользователи системы должны иметь возможность создавать файлы и каталоги в этой папке.
2. Однако ни один обычный пользователь не должен иметь права удалять или переименовывать файлы, созданные другими пользователями (только автор файла или root могут удалить свой файл).
3. Установите соответствующие права и протестируйте сценарий:
   - `dev_alice` создает файл `alice_doc.txt`.
   - `dev_bob` пытается удалить файл `alice_doc.txt`. Операция должна завершиться ошибкой `Operation not permitted`.

### Задание 3: Гранулярный доступ для отдела безопасности через POSIX ACL
Ситуация: Сотрудник ИБ `auditor_charlie` не входит в группу `developers`, но обязан проводить аудит исходного кода в `/tmp/corp_storage/projects`.
**Требования:**
1. Не добавляя `auditor_charlie` в группу `developers` и не меняя базовые права каталога (Others должны оставаться `0`), предоставьте пользователю `auditor_charlie` права на чтение и просмотр содержимого каталога (`r-x`).
2. Настройте **дефолтные (default) ACL** на каталог `/tmp/corp_storage/projects` так, чтобы на все создаваемые в будущем файлы и подкаталоги `auditor_charlie` автоматически получал доступ на чтение (`r--` для файлов и `r-x` для папок).
3. Проверьте права с помощью команды `getfacl`.

### Задание 4: Аудит безопасности sudoers и устранение GTFOBins
Откройте файл `starter_data/vulnerable_sudoers.conf`.
В нем представлены три правила, которые системный администратор настроил на сервере:
1. `junior_admin ALL=(root) NOPASSWD: /usr/bin/find`
2. `dev_alice ALL=(root) /usr/bin/vim /etc/nginx/sites-available/project.conf`
3. `backup_user ALL=(root) NOPASSWD: /usr/bin/tar -czf *`

**Вопросы и действия:**
1. Объясните, как каждое из этих трех правил позволяет пользователю мгновенно получить интерактивный root-шелл (повысить привилегии до полного root). Приведите конкретные команды побега в шелл.
2. Предложите исправленные, безопасные варианты предоставления доступа для каждого сценария.

### Задание 5: Эксплуатация SUID-бинарника через PATH Hijacking
В `starter_data/vuln_status.c` представлен исходный код служебной утилиты.
1. Скомпилируйте программу и установите на нее владельца root и бит SUID:
   ```bash
   gcc -o /tmp/vuln_status starter_data/vuln_status.c
   sudo chown root:root /tmp/vuln_status
   sudo chmod 4755 /tmp/vuln_status
   ```
2. Проанализируйте код: какую системную утилиту вызывает программа без абсолютного пути?
3. От имени обычного пользователя (`student` или `dev_alice`) создайте в каталоге `/tmp` поддельную утилиту `service`, которая копирует `/bin/bash` в `/tmp/root_shell` с битом SUID (или создает root-пользователя).
4. Модифицируйте переменную `PATH` и запустите `/tmp/vuln_status`.
5. Убедитесь в получении root-шелла.
6. Исправьте исходный код и объясните правила безопасного написания SUID-программ на C.

## 📌 Критерии приемки
- При создании файлов в `projects/` группой всегда является `developers`.
- При попытке чужого удаления в `public_drop/` возвращается `Operation not permitted`.
- `getfacl /tmp/corp_storage/projects` отображает пользователя `auditor_charlie` и блок `default:user:auditor_charlie:r-x`.
- В Задании 4 полностью расписаны механизмы побега в шелл и представлены безопасные альтернативы.
- В Задании 5 успешно продемонстрирована атака PATH Hijacking и предложен безопасный патч кода.
