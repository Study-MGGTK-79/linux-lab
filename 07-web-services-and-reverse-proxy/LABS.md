## Лабораторная работа 7.1: Аудит и эксплуатация Nginx Alias Traversal (LFI)

### 🏢 Бизнес-контекст
В ходе аудита безопасности веб-портала компании пентестеры обратили внимание на странное поведение статического контента. Приложение хранит публичные таблицы стилей и скрипты в каталоге `/var/www/app/static/`, однако в корне приложения `/var/www/app/` также расположены файл конфигурации `config.py` (содержащий мастер-пароль базы данных и секретный ключ `SECRET_KEY`) и файл `.env` с API-токенами.
Из-за ошибки в директиве `alias` веб-сервер позволяет выйти за пределы каталога статических файлов.

### 🎯 Технические требования и задачи
1. **Анализ уязвимого конфигурационного файла**:
   - Изучите файл `starter_data/vulnerable_nginx.conf`.
   - Найдите блок `location /static` и объясните, почему отсутствие замыкающего слэша в объявлении `location` порождает уязвимость выхода за пределы каталога (Off-by-slash / Alias Traversal).
2. **Практическая эксплуатация (Proof of Concept)**:
   - С помощью утилиты `curl` сформируйте запрос, позволяющий прочитать содержимое секретного файла `config.py`:
     ```bash
     curl -s -i "http://127.0.0.1:8080/static../config.py"
     ```
   - Сформируйте запрос для извлечения файла `.env`:
     ```bash
     curl -s -i "http://127.0.0.1:8080/static../.env"
     ```
   - Зафиксируйте извлеченные флаги и секретные ключи.
3. **Устранение уязвимости (Remediation)**:
   - Исправьте директиву в конфигурации Nginx, синхронизировав замыкающие слэши (`location /static/`).
   - Перезагрузите или перезапустите Nginx: `nginx -s reload` (или перезапустите процесс с обновленным конфигом).
4. **Верификация**:
   - Повторите запрос `curl -s -i "http://127.0.0.1:8080/static../config.py"`.
   - Убедитесь, что сервер возвращает код ошибки `404 Not Found` (или `403 Forbidden`), а чтение системных файлов за пределами каталога заблокировано.

### 📋 Критерии приемки (Definition of Done)
- [ ] Уязвимость успешно воспроизведена: получено содержимое `config.py` и `.env` через HTTP GET.
- [ ] Ошибка в директиве `location /static/` исправлена.
- [ ] Повторный запрос возвращает статус HTTP 404/403. Доступ к родительскому каталогу невозможен.

## Лабораторная работа 7.2: Обход IP-белого списка админ-панели через спуфинг `X-Forwarded-For`

### 🏢 Бизнес-контекст
Административная панель `/admin` бэкенд-сервиса содержит критические функции управления платежами и базами данных. Для защиты ресурса разработчики внедрили проверку IP-адреса: доступ разрешен исключительно локальному администратору (`127.0.0.1`). Однако обратный прокси Nginx был сконфигурирован с небезопасным пробросом заголовков клиента, что позволяет любому внешнему пользователю обойти проверку подлинности.

### 🎯 Технические требования и задачи
1. **Исследование механизма валидации IP**:
   - Выполните обычный запрос к админ-панели через прокси:
     ```bash
     curl -s -i http://127.0.0.1:8080/admin
     ```
   - Убедитесь, что сервер отклоняет запрос со статусом `403 Forbidden` (`Access denied: client IP is not in whitelist`).
2. **Анализ мисконфигурации Nginx**:
   - Откройте `starter_data/vulnerable_nginx.conf` и найдите блок `location /admin`.
   - Обратите внимание на директиву:
     ```nginx
     proxy_set_header X-Forwarded-For $http_x_forwarded_for;
     ```
   - Определите, почему использование `$http_x_forwarded_for` вместо `$proxy_add_x_forwarded_for` или жесткой фиксации `$remote_addr` фатально нарушает границу доверия (Trust Boundary).
3. **Эксплуатация уязвимости (IP Spoofing)**:
   - Сформируйте запрос `curl`, внедрив в заголовок `X-Forwarded-For` адрес доверенного администратора:
     ```bash
     curl -s -i -H "X-Forwarded-For: 127.0.0.1" http://127.0.0.1:8080/admin
     ```
   - Зафиксируйте успешный ответ сервера с кодом `200 OK` и полученный секретный токен доступа администратора.
4. **Устранение мисконфигурации (Hardening)**:
   - Замените небезопасную трансляцию заголовка на защищенную комбинацию:
     ```nginx
     proxy_set_header X-Real-IP $remote_addr;
     proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
     ```
   - Настройте модуль `ngx_http_realip_module` (если трафик поступает через доверенный upstream):
     ```nginx
     set_real_ip_from 127.0.0.1;
     real_ip_header X-Forwarded-For;
     real_ip_recursive on;
     ```
   - Примените изменения в Nginx.
5. **Верификация**:
   - Повторите запрос со спуфингом `X-Forwarded-For: 127.0.0.1`.
   - Убедитесь, что бэкенд видит реальный внешний IP сокета и отклоняет попытку несанкционированного доступа (HTTP 403 Forbidden).

### 📋 Критерии приемки (Definition of Done)
- [ ] Продемонстрирован обход IP Whitelist через подделку HTTP-заголовка.
- [ ] Конфигурация Nginx обновлена: клиентский заголовок не транслируется «как есть».
- [ ] При повторной попытке спуфинга доступ блокируется со статусом HTTP 403.

## Лабораторная работа 7.3: Криптографический аудит устаревшего TLS и переход на Hardened TLS 1.3 с PFS

### 🏢 Бизнес-контекст
Корпоративный сканер уязвимостей выявил критические несоответствия стандартам PCI-DSS на защищенном шлюзе (порт `8443`). Сервер поддерживает устаревшие протоколы TLS 1.0 и 1.1, подвержен атакам класса BEAST и POODLE, а в шифронаборах присутствуют статические RSA-ключи без поддержки Perfect Forward Secrecy (PFS), что создает угрозу ретроспективной расшифровки перехваченного сетевого трафика.

### 🎯 Технические требования и задачи
1. **Аудит протоколов и шифронаборов через OpenSSL**:
   - Проверьте, принимает ли сервер рукопожатие по устаревшему протоколу TLS 1.0:
     ```bash
     openssl s_client -connect 127.0.0.1:8443 -tls1
     ```
   - Проверьте поддержку протокола TLS 1.1:
     ```bash
     openssl s_client -connect 127.0.0.1:8443 -tls1_1
     ```
   - Убедитесь, что соединение устанавливается успешно, и зафиксируйте используемый шифр (например, `AES256-SHA` в режиме CBC без PFS).
2. **Проектирование Hardened SSL/TLS конфигурации**:
   - Создайте файл конфигурации с наивысшим уровнем защиты TLS:
     - Разрешить **только** современные защищенные протоколы:
       ```nginx
       ssl_protocols TLSv1.2 TLSv1.3;
       ```
     - Настроить стойкий набор шифров с обязательной поддержкой Perfect Forward Secrecy (ECDHE) и режимов AEAD (GCM / Poly1305):
       ```nginx
       ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305';
       ssl_prefer_server_ciphers on;
       ```
     - Включить параметры эллиптических кривых:
       ```nginx
       ssl_ecdh_curve X25519:prime256v1:secp384r1;
       ```
     - Настроить безопасное управление сессиями:
       ```nginx
       ssl_session_timeout 1d;
       ssl_session_cache shared:SSL:10m;
       ssl_session_tickets off;
       ```
     - Внедрить строгий заголовок **HSTS**:
       ```nginx
       add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
       ```
3. **Верификация**:
   - Повторите попытки подключения по протоколам `-tls1` и `-tls1_1`. Убедитесь, что OpenSSL завершает работу с ошибкой рукопожатия (*handshake failure / alert protocol version*).
   - Подключитесь по протоколу TLS 1.3:
     ```bash
     openssl s_client -connect 127.0.0.1:8443 -tls1_3
     ```
   - Убедитесь, что сессия успешно согласована с использованием шифра `TLS_AES_256_GCM_SHA384` или `TLS_AES_128_GCM_SHA256`, а в выводе присутствует заголовок `Strict-Transport-Security`.

### 📋 Критерии приемки (Definition of Done)
- [ ] Сервер отклоняет любые подключения по протоколам SSLv3, TLS 1.0 и TLS 1.1.
- [ ] Подключение по TLS 1.3 и TLS 1.2 успешно функционирует исключительно со стойкими шифрами ECDHE/AEAD.
- [ ] В ответах присутствует заголовок `Strict-Transport-Security`.
- [ ] Отключены сессионные тикеты (`ssl_session_tickets off;`) для гарантии PFS.

## Лабораторная работа 7.4: Защита Nginx от DoS (двухзонный Rate Limiting) и инъекция Security Headers

### 🏢 Бизнес-контекст
Публичный API шлюз компании подвергся серии распределенных атак:
1. HTTP Flood на эндпоинты API, вызвавший исчерпание пула рабочих процессов бэкенда.
2. Автоматизированный подбор паролей (Credential Stuffing) на эндпоинте `/api/login`.
3. Отчет внешнего аудита указал на полное отсутствие HTTP-заголовков безопасности, что создает риски атак Clickjacking и XSS.

### 🎯 Технические требования и задачи
1. **Проектирование двухзонного Rate Limiting**:
   - В контексте `http` объявите три зоны ограничения в оперативной памяти:
     - Зона соединений: `limit_conn_zone $binary_remote_addr zone=addr_conn_limit:10m;`
     - Зона общего API: `limit_req_zone $binary_remote_addr zone=api_general_limit:10m rate=10r/s;`
     - Зона аутентификации: `limit_req_zone $binary_remote_addr zone=auth_strict_limit:10m rate=2r/s;`
   - Переопределите статус-код превышения лимитов на `429 Too Many Requests`:
     ```nginx
     limit_req_status 429;
     limit_conn_status 429;
     ```
2. **Применение политик ограничения к виртуальному хосту**:
   - Ограничьте максимальное количество одновременных TCP-соединений с одного IP до `10`:
     ```nginx
     limit_conn addr_conn_limit 10;
     ```
   - Для пула `/api/` примените `limit_req zone=api_general_limit burst=10 nodelay;`.
   - Для критического эндпоинта `/api/login` установите жесткое ограничение:
     ```nginx
     location /api/login {
         limit_req zone=auth_strict_limit burst=2 nodelay;
         proxy_pass http://127.0.0.1:8081/api/login;
     }
     ```
3. **Внедрение комплекса Security Headers**:
   - В контексте `server` добавьте следующие защитные заголовки с обязательным флагом `always`:
     - `Content-Security-Policy`: `"default-src 'self'; script-src 'self'; object-src 'none';"`
     - `X-Frame-Options`: `"DENY"`
     - `X-Content-Type-Options`: `"nosniff"`
     - `Referrer-Policy`: `"strict-origin-when-cross-origin"`
     - `Permissions-Policy`: `"geolocation=(), camera=(), microphone=()"`
   - Отключите раскрытие версии сервера: `server_tokens off;`.
4. **Нагрузочное тестирование и верификация**:
   - Выполните пакетную серию из 10 быстрых запросов к `/api/login`:
     ```bash
     for i in {1..10}; do
         curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/api/login
     done
     ```
   - Убедитесь, что первые 2-3 запроса возвращают код `200`, а последующие немедленно отсекаются с кодом `429`.
   - Проверьте наличие всех защитных заголовков в ответе:
     ```bash
     curl -s -I http://127.0.0.1:8080/api/public
     ```

### 📋 Критерии приемки (Definition of Done)
- [ ] При превышении порога запросов на `/api/login` сервер возвращает HTTP статус `429 Too Many Requests`.
- [ ] Заголовок `Server` не содержит номера версии Nginx.
- [ ] В ответах присутствуют заголовки `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`.
- [ ] Решения проверены с помощью скрипта автоматической валидации `starter_data/exploit_test.sh`.
